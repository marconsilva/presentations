What is a Coding Agent?

A coding agent is an AI system that autonomously performs software engineering tasks.

  • It plans the work before writing code
  • It executes multi-step implementations
  • It reviews its own output and iterates
  • It ships code through PRs and CI/CD

Autocomplete vs. Agent

Dimension Copilot (Autocomplete) Coding Agent
Scope Single line / block Entire feature / system
Initiative Reactive (waits for you) Proactive (plans & acts)
Context Current file Full repository + tools
Output Code suggestion PR with tests & docs
Loop Single-shot Plan → Act → Review → Iterate

Multi-Agent Teams That Deliver

The Limitation of a Single Agent

One agent can do a lot. But real engineering isn't a solo sport.

  • Who reviews the agent's code?
  • Who writes the tests?
  • Who handles the architecture decisions?

You need a team. An agent team.

What is Squad?

Squad is an open-source framework by Brady Gaster that turns GitHub Copilot into a persistent, multi-agent engineering team living in your repository.

Describe what you're building. Squad coordinates specialist agents that grow with your code. You spend less time prompting, more time deciding.

🐙

GitHub-Native

Lives as .squad/ in your repo — commit, share, clone

🧠

Persistent Memory

Agents remember decisions and conventions across sessions

🛡️

Built-in Governance

File-write guards, reviewer lockout, escalation points

⚡

SDK-First

TypeScript config (squad.config.ts) — typed and testable

How Squad Forms Your Team

Squad analyses your repository and proposes a roster of 3–7 specialist agents:

Default roles detected:

🏗️ Lead (always) · 💻 Core Dev (always) · 🧪 Tester (if tests detected) · ⚛️ Frontend (if React/Vue found) · 🔧 Backend (if APIs found) · 📋 Scribe (always — silent memory logger)

The .squad/ Directory — Your Team's Brain

.squad/
├── team.md                 # Team roster & roles
├── routing.md              # Work routing rules
├── decisions.md            # Persistent team memory
├── ceremonies.md           # Design reviews, retros
├── agents/
│   ├── hicks/
│   │   ├── charter.md     # Identity, skills, voice
│   │   └── context.md     # Cross-session learnings
│   ├── ripley/
│   └── dallas/
├── skills/                 # Reusable capabilities
└── casting/                # Team formation history

Commit it to version control. Anyone who clones gets the full team with all their knowledge.

Parallel Fan-Out — The Launch Table

Say "Team, build the recipe listing page" and agents fan out:

🏗️ Hicks Defining API contract, pagination strategy
⚛️ Ripley Building React component with data fetching
🔧 Dallas Creating API endpoint, connecting to database
🧪 Lambert Writing test cases from requirements — proactively
📋 Scribe Logging decisions, merging context (silent)

All agents work simultaneously in separate context windows.

Routing & Reviewer Protocol

Work gets to the right agent automatically (first match wins):

Strategy Example
Named "Dallas, fix the login bug"
Domain src/api/** → Backend agent
Skill-aware Auth expertise → Lead or Backend

🔒 Reviewer Lockout

If a reviewer rejects code, the author agent is locked out — no self-revision. Work is reassigned or escalated to you. This prevents endless fix-retry loops.

Ceremonies & Persistent Memory

🎨 Design Review

Auto-triggers when 2+ agents modify shared systems. Lead facilitates discussion on interfaces and risks.

🔄 Retrospective

Auto-triggers on build failures or reviewer rejections. Root-cause analysis → decisions written for future.

📌 Decisions accumulate over time:

### 2025-07-15: React Query for data fetching
By: Ripley | Why: Built-in caching and loading states

### Directive: Always use Zod for API validation

Why Squad Works

  • Human-directed — you set direction, review results, keep final decision
  • Specialization — each agent has a charter, voice, and expertise
  • Parallel by default — say "team" and agents fan out concurrently
  • Self-aligning — accumulated decisions keep agents consistent
  • Inspectable — everything is markdown files in your repo

"Responsible AI, explicitly" — agents extend your team, not replace it.

Spec2Cloud Flow

Anatomy of a Good Specification

# Functional Specification: User Authentication Service

## Overview
A REST API service handling user registration, login,
and token management for the e-commerce platform.

## Functional Requirements
- Users can register with email + password
- JWT-based authentication with refresh tokens
- Rate limiting: 5 failed attempts → 15min lockout

## Technical Requirements
- Runtime: .NET 8 Minimal APIs
- Database: PostgreSQL with EF Core
- Deployment: Azure Container Apps
- Monitoring: Application Insights

## Acceptance Criteria
- All endpoints return proper HTTP status codes
- 99.9% uptime SLA
- Response time < 200ms p95

Trust & Governance

Agents at scale require guardrails:

  • Audit Trail — every agent action is logged in git history
  • Human-in-the-Loop — merge gates require human approval
  • Scope Boundaries — agents operate within defined repos/files
  • Quality Gates — CI must pass before any merge
  • Rollback — every change is a PR that can be reverted
