What Is Spec-Driven Development?

A workflow where the specification is the primary source of truth for behavior, interfaces, tests, and deployment intent.

Contract

Because architecture debates are cheaper in YAML than in production.

The Spec-First Philosophy

Traditional path

Code First

  • Endpoints appear before naming is aligned.
  • Tests chase implementation details.
  • Infra decisions get bolted on at the end.
  • Documentation becomes archaeology.

Spec-first path

Contract Before Code

Authoring

OpenAPI Spec Authoring with Copilot

Prompting pattern

  • Describe domain, actors, operations, and constraints.
  • Ask for resource model, paths, status codes, and examples.
  • Iterate on vocabulary before accepting generated YAML.

Copilot's role

  • Accelerates first draft creation.
  • Surfaces edge cases and missing responses.
  • Helps normalize naming, schemas, and examples.
# Prompt Copilot
Create an OpenAPI 3.1 spec for a work-item service.
Include CRUD operations, pagination, auth headers,
error responses, and examples for create/update flows.

Quality

Spec Best Practices

Design for readers

  • Name resources by business capability, not table names.
  • Use explicit status codes and error payloads.
  • Model pagination, filtering, and idempotency early.
  • Keep examples realistic enough for test fixtures.

Design for generators

  • Prefer reusable schemas over copy-paste payloads.
  • Constrain enums, formats, and required fields.
  • Define auth and headers once, then reference them.
  • Capture non-functional intent in extensions or notes.

Hands-on Exercise 1

Write Your First Spec

Working in pairs, define the first version of an API contract for a cloud-native service your team could actually build.

Duration: 30 min Tooling: Copilot + editor Output: OpenAPI 3.1 YAML
  • Choose one bounded context and 2-3 core resources.
  • Generate a first draft with Copilot, then refine names and rules.
  • Add at least one validation rule, one auth requirement, and one example.

Generator-ready

Schemas and operations are explicit enough to scaffold code.

Review-ready

Questions are visible in the contract instead of hidden in code.

Hands-on Exercise 2

Generate the Implementation

Use Spec2Cloud to turn your contract into a runnable service baseline and inspect what was created automatically.

Duration: 35 min Focus: generation review Output: app scaffold

  • Compare generated code back to the spec and flag gaps or ambiguities.

AFTERNOON: BROWNFIELD

Now use the same method on systems that already exist, where the contract is hidden inside legacy code and tribal knowledge.

The Brownfield Challenge

Unknown behavior

Real API behavior differs from outdated docs.

Hidden coupling

Change one endpoint and three downstream consumers break.

Fear tax

Teams avoid modernization because they cannot see the contract.

Reality check

How Legacy Apps Reveal Missing Specs

Symptoms

  • Controllers contain business rules and transport logic mixed together.
  • Swagger docs lag behind what production actually returns.
  • Only end-to-end tests know the truth.
  • Infra setup lives in scripts nobody wants to touch.

Opportunity

  • Mine logs, tests, and code for current behavior.
  • Capture current contract before changing internals.
  • Create a modernization target with explicit deltas.
  • Refactor behind a stable spec boundary.

Modernization

Spec2Cloud for Brownfield Modernization

Parallel tracks

  • Preserve the current contract while generating a cleaner target.
  • Produce adapters, tests, and rollout scaffolding from specs.
  • Use contract tests to prove parity before cutover.

Controlled change

  • Deprecate endpoints with explicit versioning guidance.
  • Validate migrations in lower environments automatically.
  • Ship modernization as governed increments, not rewrites.

Hands-on Exercise 6

Execute the Modernization

Use the target spec to generate the modernization path and prove that behavior is intentional, traceable, and deployable.

Duration: 35 min Focus: safe execution Output: modernization plan
  • Generate updated implementation stubs, tests, and rollout artifacts.
  • Validate parity for unchanged behavior and explicit deltas for new behavior.
  • Define a release sequence: shadow, canary, or cutover.

Craft

Best Practices for Writing Effective Specs

Precise

Constrain types, validation rules, and error semantics clearly.

Observable

Include examples and behaviors that can be tested automatically.

Portable

Separate business contract from cloud-specific implementation details.

Reviewable

Treat specs like code: PRs, comments, versioning, ownership.

Evolvable

Document backward compatibility and deprecation paths.

Operational

Let the contract feed tests, infra, deployment, and governance.

Anti-Patterns to Avoid

Spec as documentation only

If it does not influence generation or validation, it will drift.

Copilot without constraints

AI is faster when the contract narrows the solution space.

Big-bang modernization

Recover the current contract before chasing the ideal future state.

Cloud intent as an afterthought

Non-functional requirements belong near the spec, not in a late ticket.

Take-home

Methodology Reference

  1. Frame the capability

    Define the user outcome, business rules, and quality constraints.

  2. Author or recover the spec

    Use Copilot to accelerate drafting, then review and tighten it.

  3. Generate from the contract

    Create code, tests, and cloud assets with Spec2Cloud.

  4. Validate continuously

    Run contract checks locally, in CI, and against deployed environments.

  5. Evolve intentionally

    Version the contract, deprecate clearly, and modernize behind stable boundaries.
